What it is

Two ways to say it

The company

Limonada S.L.

A made up juice distributor with 40 staff. It's the same company that runs the web shop I protected in my WAF project, so the two projects tell one story.

The company lives on a private VMware network and the SOC lives outside it, in Docker. That's how a managed SOC works in real life too: it sits outside the client's network and the logs travel to it.

    Alert queue

      The ten detections

      In the order an intruder trips them

      Each detection is a saved SPL search that runs every minute over the last fifteen, mapped to a MITRE ATT&CK technique. The serious ones page my phone. The quieter ones sit on the dashboard as context, so the pager stays meaningful.

      The pager

      Alerts are no use if I'm not staring at the screen

      1. Splunk alert
      2. relay.py
      3. private ntfy topic ••••••
      4. my phone

      A Splunk alert calls a small relay I wrote, which forwards it to a private ntfy topic that my phone is subscribed to. The topic name is a secret kept out of the repo, so nobody else can read my alerts.

      Only High and Critical page. Medium detections stay on the dashboard, because a pager that cries wolf gets ignored, and that is a real way a SOC fails.

      Why a relay and not Splunk straight to ntfy: the topic works like a password. With the relay it lives only in .env, which Git ignores, instead of in savedsearches.conf.

      What I found

      The part I'd talk about in an interview

      The detections are the point, but the findings along the way are what I'd actually talk about.

      How I learned it

      A driving instructor with dual controls

      I'm still learning, so I built this the way a lot of people learn now: with Claude Code, an AI coding assistant, as my tutor. It helped me script the lab, the domain build, the configs and the first drafts of the detections.

      I used it to learn the job, not to skip it: I ran Limonada S.L. on my own machines, ran every attack, debugged every detection that came back empty, and worked out the findings myself.

      Think of a driving instructor with dual controls. The instructor helped get the car on the road; I'm the one learning to drive it.

      What this taught me

      This doesn't make me a finished analyst. It makes me someone who has done the work with their own hands and can talk through every piece of it, which is where I want to be starting from.

        Limits

        This is a training lab for one analyst, not real security for a real company. It's a handful of virtual machines on one PC, not a hardened network, and the SOC is one person working by hand, not Splunk Enterprise Security or a 24/7 team. The worth of it is in the building and the understanding, not in the scale.

        About me

        I'm Albeen

        I'm studying network systems administration and I want to start my career as a SOC analyst. Before this I did a CyberSOC trainee program and guided Elastic and Kibana labs.

        The trouble with guided labs is that someone else has already built the company, planted the attack and handed you the clean logs. You end up practising how to read the answer, not how to find it. So I built the whole thing myself.

        The point was never to collect ten working searches. It was to understand the whole chain, from the command an attacker types, to the log line it leaves, to the alert on my phone, so I can explain any piece of it out loud.
